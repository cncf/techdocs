#### Recommendations, requirements, and best practices

This analysis measures documentation against CNCF project maturity standards,
and suggests possible improvements. In most cases there is more than one way to
do things. Few recommendations here are meant to be prescriptive. Rather, the
recommended implementations represent the reviewers' experience with how to
apply documentation best practices. In other words, borrowing terminology from
the lexicon of [RFCs](https://www.rfc-editor.org/rfc/rfc2119), the changes
described here should be understood as "recommended" or "should" at the
strongest, and "optional" or "may" in many cases. Any "must" or "required"
actions are clearly denoted as such, and pertain to legal requirements such as
copyright and licensing issues.

#### Core website requirements

The core, or minimal, set of requirements include a check that source files for
_all website pages_ should reside in a single repo. Among other problems,
keeping source files in two places:

- confuses contributors
- requires you to keep two sources in sync
- increases the likelihood of errors
- makes it more complicated to generate the documentation from source files

Ideally, all website files should be in the **website repo** itself.
Alternatively, files should be brought into the website repo via git submodules

If a project chooses to keep source files in multiple repos, they need a clearly
documented strategy for managing mirrored files and new contributions.

The core requirements also include criteria for maturity levels but are
applicable to all maturity levels.

#### Usability, accessibility and devices

Most CNCF websites are accessed from mobile and other non-desktop devices at
least 10-20% of the time. Planning for this early in the website's design will
be much less effort than retrofitting a desktop-first design.

- [mobile-first](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Responsive/Mobile_first)
- [accessibility](https://developer.mozilla.org/en-US/docs/Web/Accessibility)

It is up to each project to set their own guidelines.

#### AI Agent Readiness

AI agents—coding assistants, bots, and agentic search tools—increasingly read
documentation on a user's behalf, making them a new audience alongside human
readers. Preparing your site for them lets agents retrieve accurate, up-to-date
answers and send users back to the project, rather than relying on stale or
third-party sources that can misrepresent it. Many agent-readiness practices,
such as serving clean Markdown, rendering content server-side, and publishing an
`llms.txt` index of your key pages, also make the documentation faster, more
portable, and easier to maintain.
